# Field Atlas: implementation and rollout

## Roles and lifecycle

Staff interface: `/world/` (admin and assigned team). Farmer interface: Flutter
Farmer app (owned field names, requests, progress, released reports). The existing
Team app remains the field notebook, including encrypted offline drafts and
explicit syncing. No physical Arduino connection is required to demonstrate
this workflow; measured versus simulated temperature must be declared accurately.

`pending -> approved -> in_progress (optional) -> awaiting_review -> completed`.
Admin may reject an open visit. There can be only one open visit per field.
Booking/assignment/submission/release update the world and survey in the same
Firestore batch with version preconditions. Stale screens receive HTTP 409.
An accepted offline submission ID can be retried only with the identical payload,
including compatibility for old payloads that predate moisture-basis metadata.

## Data and APIs

- `farms/plot-NNNNN`: stable farmer-owned field, crop preset, slot, care policy,
  monotonically increasing version, latest survey/assignment and staff assessment.
- `farm_assessments/{submissionId}`: immutable submission snapshot, including
  grading method, policy bands/units/reference, provenance, findings and warnings.
- `survey_predictions/{surveyId}`: private care draft and admin report draft.
- `farm_inputs/{surveyId}`: existing owned survey; approved farmer copy is added
  only when admin publishes. Internal care assessment stays outside this document.
- `survey_email_events`: existing transactional, best-effort status notifications;
  completed notifications include the reviewed summary, actions and notices.

Staff: `GET /world/session`, `GET /world/assets`, `GET /world/farms`,
`GET /world/farms/{id}`, `GET /world/events`.
Admin: `POST /world/farms`, `POST /world/farms/{id}/link-survey`,
`POST /world/farms/{id}/policy`,
`GET|POST /world/surveys/{id}/report?language=en|hi|mr`.
Farmer: `GET /farm/fields` (metadata only), existing survey APIs with optional
`farmId` during booking. Old APK requests can be linked while still pending.

Only admin creates regions/changes policies or prepares/releases reports.
Inspectors see farms assigned to their UID. Direct Firestore client writes are
denied. Farmer-owned metadata is delivered through the authenticated API, not
world collections. Tokens stay in memory and in Bearer headers, never query
strings. Event streams expire/reconnect after 180 seconds, recheck profile role
at least every 15 seconds, and unsubscribe their Firestore listener on close.
Polling provides recovery if the listener is unavailable. This is near-real-time
after submission, not a continuous gadget connection.

## Care policy and honest interpretation

A/B/C count out-of-band moisture, temperature, N and K readings. A means no
flagged readings under that policy; it does not certify a healthy farm. U means
missing readings or incompatible moisture/nutrient units under documented rules.
Default example bands: moisture 30-70%, temperature 18-35 C, N/K 50-500 raw units.
These arbitrary prototype bands are visibly labelled demonstrations. They are
not validated for any crop, location, season or soil. No health-class dataset
has been invented or claimed. The old rainfall/crop datasets are not used here.

Admin may supply documented bands and a reference when creating a field.
The versioned policy-update API permits later edits only without an open visit.
Configured nutrient units must be mg/kg or kg/ha. A matching declared moisture
basis (relative calibration % versus volumetric %) is mandatory for a verified
configured-rule result. Different units produce U; no conversion is assumed.
Manual input and simulated temperatures retain warnings; an admin-entered
reference is not independent agronomic validation. Before operational use,
validate crop/soil-specific bands with a qualified local agronomist and establish
measurement/calibration procedures. Classes organise follow-up, not diagnoses,
fertiliser dosages, crop recommendations or yield guarantees.

Farmer report templates are provided in English, Hindi and Marathi. Admin edits
and approves the summary and one to six next steps. Mandatory limitation/source
notices are generated by the backend and cannot be removed via request data.
Saved drafts remain private; published reports cannot be silently overwritten.
Reports are structured in-app text, not attached PDF files. The chatbot may use
the approved summary and notices; it does not create admin messages or visit jobs.

## World rendering and scale

Six original procedural meshes are bundled as reusable crop presets. The 3D
scene supports field picking, keyboard/list selection, orbit, pan, zoom, class
filters and a focus view. Changes animate foliage colour/height over 1.5 seconds;
reduced-motion preference applies instantly. These are symbolic care-state
animations, not observations of plant growth or degradation. A list/detail
fallback remains usable when WebGL is unavailable.

World region positions use a stable six-column illustrative grid, not satellite
imagery or real boundaries. Up to 10,000 unique region numbers can be stored.
The UI loads 200 fields at a time and caps its live window at 1,000 loaded fields.
It has not been load-tested at that scale; it is a prototype for a modest pilot,
not a claim of large-world performance. Use the directory and focus view for
navigation. Real GPS polygons, imported 3D models and geographic tiling are future
extensions, not included features.

## Validation and rollout

Local checks: `python -m pytest -q`,
`node --test world_web/tests/*.test.js admin_web/tests/*.test.js`,
`dart analyze lib test` from `mobile/`.
Backend tests substitute Firestore and cloud identity; they do not send email or
contact production Firebase. The suite covers ownership, role/assignment scope,
canonical field booking, concurrent update rollback, classes/units/boundaries,
private drafts, report release, class history, retries and legacy compatibility.
Web tests cover real geometry/matrices, picking, state transitions, directory
filters, parser chunking and authenticated live-fetch requests, alongside the
existing admin tests. Firebase emulator tests also specify world access rules.

The original implementation was checkpointed before this pivot. Render currently
tracks the old branch; pushing `codex/3d-farm-world` does not deploy this feature.
To roll out, review the branch, deploy the updated backend and Firestore rules,
then build/install updated Farmer and Team APKs using `update_apps.bat` or
`scripts/build_android.ps1` (JDK 17 / Flutter setup required). Keep existing
Firebase/Gmail/Gemini secrets in environment/private local files. No new paid
service or cloud resource is required by this implementation.

Live Firebase subscriptions, real-user cross-device updates, actual email inbox
delivery, new APK installation and physical field measurements still require
an environment-backed pilot after deployment. API/unit tests do not establish
agronomic accuracy or certify those operational integrations.
